## Purpose and controlling rule

This is the implementation handoff for Phase 6 — Staff and managers can run the business. It does not mark Phase 6 as started or finished. It begins with the required audit of Phases 1–5 because Phase 6 depends on their people, vehicle, inquiry, recommendation, and transaction records.

The audit found that the statement “Phases 1–5 completed” is not supported by the current code. Several features have only a table or unused server function, later migrations disable the row-level security described by the tracker, and the production build does not pass. Under the status legend, a finished item must be built, checked, and working. No phase currently meets all three conditions as a complete phase.

The implementation order is mandatory:

1. Complete Recovery Gates 0–3.
2. Record approved answers to every decision gate that affects the next workstream.
3. Implement Phase 6 in the workstream order in this plan.
4. Pass the verification gates before changing any Phase 6 tracker item to finished.

## Audit method and limits

The audit compared each Phase 1–5 roadmap item with the current `src/`, `supabase/migrations/`, scripts, routes, and UI call sites. It also ran the repository checks on 8 August 2026:

- `npm run build` compiled the application bundle but failed during TypeScript checking in Phase 5 customer transaction screens.
- `npx tsc --noEmit --pretty false` reported 19 TypeScript diagnostics.
- `npx biome check src` reported 16 errors in the source tree.
- No automated test framework is currently configured, so no repeatable unit, database-policy, or browser acceptance suite proves the completed claims.
- No live production database, deployed environment, or complete authenticated browser journey was changed or treated as verified by this documentation task.

Severity in the tables means:

| Severity | Meaning |
|---|---|
| P0 | Security, credential, authorization, or build failure that blocks all later work |
| P1 | Required journey is missing, unreachable, unsafe, or materially incomplete |
| P2 | Supporting behavior, evidence, or documented quality is incomplete |
| P3 | Documentation or maintainability discrepancy that does not independently block a journey |

## Recovery Gate 0 — Credentials, authorization, and build

No later gate begins until all Gate 0 evidence is recorded.

### 0.1 Rotate and remove exposed credentials

- Treat the database credential stored in the tracked migration helper as compromised.
- Rotate the database credential and Supabase service-role key in the service provider and every deployment environment before removing the old values from the current tree.
- Replace tracked connection values with `DATABASE_URL` or narrowly named environment inputs. Make the seed-user password an explicit local/test environment input and never print it.
- Redact shared passwords from [13 - USER ACCOUNTS](13%20-%20USER%20ACCOUNTS.md); retain account purposes and addresses only if they are approved non-production test identities.
- Run a full-history secret scan. The approved policy is **rotate and preserve Git history**; do not force-push or rewrite history after the old values are invalid.

**Gate evidence:** provider rotation time, deployment-secret update confirmation, current-tree secret scan with zero active secrets, full-history scan report, and successful connection using only environment configuration.

### 0.2 Restore database isolation with forward migrations

- Do not edit already-applied migrations `00010` or `00012`.
- Add `00013_restore_rls_and_secure_role_rpcs.sql` to re-enable RLS on every public Phase 1–5 table, revoke unsafe function grants, replace role functions with actor-derived authorization, and restore least-privilege policies.
- Ensure private tables are unavailable through direct client access and storage objects follow the same record ownership rules.

**Gate evidence:** clean local `supabase db reset`; pgTAP matrix proving anonymous, customer, supplier, every staff role, and service-role access; zero policy-recursion errors.

### 0.3 Centralize action authorization and ownership

- Introduce one server-only authorization boundary that resolves the authenticated user and active database role; never trust a client-writable role cookie for authority.
- Every server action must declare allowed roles and validate record ownership before using a normal or administrative Supabase client.
- Administrative clients may be used only after authorization, for the smallest required write, with an audit event containing actor, action, record kind, record ID, and outcome.
- Standardize action responses as `ActionResult<T> = { ok: true; data: T } | { ok: false; code: string; message: string; fieldErrors?: Record<string, string[]> }`.

**Gate evidence:** unit tests for the guard and Playwright attempts proving URL manipulation, cookie editing, direct action invocation, and cross-account IDs are denied.

### 0.4 Repair authentication, routing, and compilation

- Make password sign-in, email callback, registration, sign-out, and session refresh set or derive one canonical database role and land on the correct role-prefixed URL.
- Keep the external `/{role}/...` contract and internal role-group rewrite, but remove obsolete `/dashboard/default` assumptions from active flows.
- Resolve all TypeScript and Biome errors without weakening strict mode or disabling rules.

**Gate evidence:** `npx tsc --noEmit`, `npx biome check src`, and `npm run build` all exit successfully; Playwright covers fresh customer registration and one account for every role.
