# Objective
## Staff Records Page Table Redesign and Error Resolution

---

## Role
You are a frontend UI/UX developer with debugging expertise, specializing in template-driven component reuse and error diagnosis. Approach this objective with a focus on exact table replication, systematic error investigation, and root-cause resolution.

---

## Description
The objective is to redesign the Staff Records page located at http://localhost:3000/{users}/staff-records by replacing the existing table with the exact customers table design from the Default template dashboard. The template table must be replicated with complete fidelity, preserving the search box, filter dropdowns, pagination controls, table layout, styling, and all columns without modification — only the data content and the Action column's context menu items may be adapted. Additionally, two persistent error messages must be investigated and resolved: "Staff records are temporarily unavailable. Please refresh and try again." and "Performance reviews are temporarily unavailable. Please refresh and try again." The root cause of these errors must be identified and fixed so that both staff records and performance reviews load correctly.

---

## Detailed Breakdown

### Table Design Fidelity Requirement
The customers table from the Default template dashboard must be replicated with absolute fidelity. This includes the search box with its exact placeholder text, input styling, and search behavior; all filter dropdowns with their options, styling, and interaction patterns; pagination controls with their exact layout, button styling, and page size options; the table layout including column widths, alignment, header styling, and row treatments; and all visual styling including borders, spacing, typography, hover states, and alternating row colors if present. The only permitted deviations are the data content populating the rows and the actions available in the Action column's context menu. The three-dots icon (⋮) that triggers the context menu must remain unchanged.

### Error Investigation Methodology
Each error must be investigated systematically to identify the root cause. The investigation should examine the complete data flow: frontend component state management and data-fetching hooks, API call configuration including endpoint URLs and request parameters, network responses and HTTP status codes, backend service availability and route handlers, database query execution and data availability, and error-handling logic that transforms failures into user-facing messages. The fix must address the underlying issue rather than catching and suppressing the error message.

### Potential Root Cause Categories
The errors may originate from several common sources: a misconfigured API endpoint URL that returns a 404 or 500 response, an authentication or authorization failure preventing data access, a backend service that is not running or has crashed, a database table or collection that is empty or inaccessible, a network-level failure such as CORS or timeout issues, incorrect data transformation logic that throws an exception, or a frontend conditional that incorrectly triggers the error state even when data is available. Each of these categories must be evaluated and eliminated during investigation.
