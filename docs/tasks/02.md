## Detailed Breakdown

### Documentation as the Primary Source of Truth
Always begin work by reviewing the `docs` folder. Decisions about implementation approach, architecture, sequencing, standards, project status, and UI integration must be grounded in the existing documentation rather than assumptions made independently of it.

Relevant documentation should be consulted before beginning each portion of the Phase 2 work.

If documentation and existing implementation appear to conflict, investigate the applicable project decisions and documented source of truth before proceeding rather than silently inventing a new approach.

### Following the Roadmap Sequence
Because Phase 1 has already been completed, the next area of work is **Phase 2 — Vehicles Can Be Found and Understood**.

Review the roadmap and related documentation carefully to determine what Phase 2 requires and the proper order in which its tasks should be completed. Follow that documented sequence throughout implementation.

Do not reorder Phase 2 work based solely on convenience if the project documentation establishes dependencies or a prescribed sequence.

### UI Implementation Rules
For all Phase 2 user interface work:

- **Do not create custom UI designs.**
- Use the existing **shadcn UI templates, components, widgets, layouts, examples, and reusable patterns located in the `template` folder**.
- Treat the `template` folder as the primary source of truth for visual and component implementation.
- Reuse existing components before considering creation of new ones.
- Prefer existing shadcn component composition over bespoke component structures.
- Preserve the established spacing, typography, sizing, interaction patterns, states, responsive behavior, and general visual language represented by the templates.
- Do not introduce a separate design system, custom styling convention, or visually unique treatment for Phase 2.
- Do not redesign a shadcn/template component merely for aesthetic preference.
- Only modify or extend template-based components when required for documented functionality, accessibility, application state, data handling, routing, or technical integration.
- When a required UI can be represented by an existing template widget or pattern, use that implementation rather than building a custom equivalent.
- Keep any unavoidable additions consistent with the closest existing template pattern and minimize deviation from it.

The goal is to make Phase 2 feel like a direct continuation of the existing template-driven application, not a separately designed feature.

### Keeping Documentation Current
Once implementation is complete, update every documentation artifact affected by the changes.

This includes project trackers, implementation statuses, roadmaps, guides, architectural notes, frontend/UI guidance, and any other files whose contents should change to reflect the latest project state.

Documentation should reflect both the completed functionality and any relevant implementation details necessary for future phases to continue using the established architecture and template-driven UI approach.
