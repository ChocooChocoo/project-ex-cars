## Role

Approach this objective with a focus on identifying, documenting, and providing solutions for customer-facing issues while ensuring alignment with the documented system specifications.

## Description

Conduct a comprehensive audit of customer testing issues identified during system validation. This includes investigating three specific bugs/errors encountered in the customer portal, understanding the purpose of non-functional UI elements, and providing UI consistency recommendations. The audit will involve reviewing the docs folder as the primary source of truth for project rules and system architecture, examining error logs and system behavior, and proposing solutions that align with both the capstone documentation and the established design patterns from the shadcn template. The objective is to identify root causes, document findings, and provide actionable recommendations for resolution and UI standardization.

## Detailed Breakdown

### Showroom Payment Method Validation Error Analysis

#### Issue Description
The error "Invalid option: expected one of 'cash'|'financing'|'cheque'|'down_payment'" indicates that the system is encountering a payment method value that is not in the expected list.

#### Root Cause Investigation
The investigation will examine:
- The list of valid payment methods defined in the system
- Where the "down_payment" value is being set or passed
- If there's a discrepancy between the frontend options and backend validation
- Whether "down_payment" should be a valid option or if this is a data quality issue
- The payment method field definitions in the database schema
- Any recent code changes that might have affected payment method handling

#### Expected Behavior Based on Documentation
Review the capstone documentation to understand:
- What payment methods the system should support
- Whether "down_payment" is a legitimate payment method or a status
- The intended workflow for showroom payment processing

#### Nested Details
- Check the frontend component where payment method is selected
- Review the API endpoint that processes the payment
- Examine the database schema for the related table
- Look for any transformations or mappings that might be converting values
- Check if the error is coming from a validation schema or database constraint

### Inquiries "Assign to Me" Button Investigation

#### Issue Description
When clicking the "Assign to Me" button, nothing appears to happen, indicating either a silent failure, missing visual feedback, or a functional issue.

#### Purpose Analysis
The "Assign to Me" button likely serves to:
- Assign the inquiry to the currently logged-in user
- Change the inquiry's status to "assigned" or "in progress"
- Claim ownership of the inquiry for follow-up
- Update the inquiry's assigned_to field in the database

#### Root Cause Investigation
The investigation will examine:
- The button's event handler and what action it triggers
- Whether the API call is being made successfully
- If there are permission or role-based restrictions preventing assignment
- Whether the assignment logic requires additional validation
- If there's a status or state condition that must be met before assignment
- Whether visual feedback is being suppressed or not implemented

#### Expected Behavior Based on Documentation
Review the capstone documentation to understand:
- The intended workflow for inquiry assignment
- What roles should be able to assign inquiries
- What happens after an inquiry is assigned
- The expected user experience and feedback

#### Nested Details
- Check the network tab for API requests when the button is clicked
- Review the server-side logic for the assignment operation
- Examine any console errors or warnings
- Look for state management updates after assignment
- Check if the inquiry must be in a specific status to be assignable
- Verify if the current user has permission to perform assignments

### Request-a-Car Row-Level Security Policy Violation

#### Issue Description
The error "new row violates row-level security policy for table 'vehicle_requests'" indicates that RLS is preventing the insertion of a new record.

#### Root Cause Investigation
The investigation will examine:
- The RLS policy definition for the vehicle_requests table
- What conditions the policy enforces
- The current user's role and attributes
- What data is being inserted that fails the policy check
- Whether the policy is too restrictive for the intended use case
- If the application is sending incorrect data or missing required fields

#### Expected Behavior Based on Documentation
Review the capstone documentation to understand:
- Who should be able to create vehicle requests
- What data is required for a vehicle request
- The intended security model for vehicle_requests
- Whether customers can create their own requests

#### Nested Details
- Examine the RLS policy using SQL queries
- Check the user's session and JWT claims
- Review the INSERT operation and the data being submitted
- Verify if there's a bypass or policy exception for certain roles
- Check if the policy uses any functions or conditions that might fail
- Review the trigger or constraint definitions on the table
- Determine if the policy should be updated or if the application logic needs adjustment

### UI Consistency Recommendations

#### Current State Assessment
Review all customer-facing pages to understand the current layout:
- Which pages use the navbar-only approach
- Which pages already use the portal layout with sidebar
- The consistency of navigation across different sections
- The placement and organization of menu items

#### Target State Based on shadcn Template
The shadcn template provides a standardized portal layout with:
- A persistent sidebar containing all navigation menus
- A header area with user information and quick actions
- Main content area for page-specific content
- Consistent layout across all pages

#### Standardization Approach
Recommendations will include:
1. **Sidebar Implementation**: Replace the navbar-only navigation with a persistent sidebar on all customer-facing pages
2. **Menu Organization**: Group navigation items logically (Dashboard, Showroom, Inquiries, Request-a-Car, Profile, etc.)
3. **Header Consistency**: Standardize the header across all pages with user avatar, notifications, and logout
4. **Content Area**: Maintain consistent padding and layout for the main content
5. **Responsive Behavior**: Ensure the sidebar collapses appropriately on mobile devices
6. **Active State**: Highlight the current page in the sidebar navigation

#### Implementation Considerations
- Review the current Next.js layout structure
- Identify if a layout file already exists for authenticated users
- Determine the best approach for consistent sidebar integration
- Ensure the sidebar includes all navigation items from the current navbar
- Maintain accessibility standards
