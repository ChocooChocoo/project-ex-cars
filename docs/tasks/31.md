# Objective

## Audit and Simplify Modules Across All User Levels

---

## Role

You are a user-level process and module auditor. Approach this objective by evaluating each user account from a practical business and workflow perspective, focusing on necessity, relevance, simplicity, and preservation of essential processes.

---

## Description

Conduct a structured audit of every user level, beginning with the CEO and continuing through the remaining user levels in chronological order. For each user level, review the modules and processes available to that account and determine whether they are necessary, relevant to the user's responsibilities, and appropriately designed for that role. Identify processes that are unnecessarily complex and determine whether they can be simplified without removing important functions, controls, or essential workflow steps. Document findings as clear, non-technical recommendations only; no code changes should be made during this audit.

---

## Primary Objective

Audit every user level and its assigned modules to determine what is necessary, relevant, overly complex, removable, revisable, or suitable for simplification while preserving essential functionality and processes.

---

## Secondary Objectives

* Confirm whether each module is appropriate and necessary for the specific user level or employee role that receives access to it.
* Evaluate whether each module's current process is unnecessarily complex.
* Identify opportunities to minimize or simplify workflows without removing important parts of the process.
* Identify modules with little or no relationship to the responsibilities of the user level and recommend them for removal or revision.
* Produce a separate audit report for each user level.

---

## Success Criteria

* Every user level is audited, beginning with the CEO and continuing through the remaining user levels.
* Each relevant module is evaluated for purpose, necessity, role relevance, process complexity, and opportunities for simplification.
* Unnecessary or unrelated modules are clearly identified with recommendations for removal or revision.
* Necessary modules include a simple explanation of why they should remain.
* Each user-level audit is saved under `docs\report`.
* The CEO audit is saved as `REPORT-CEO.md`.
* Remaining user-level reports follow the same user-specific report naming approach.
* Reports remain concise, understandable, and non-technical.

---

## Constraints

* Use only the useful and necessary agents available in `.opencode\agents`.
* Use parallel agents and sub-agents for exploration where appropriate.
* Do not make code changes during this audit.
* Recommendations for removal or revision must remain suggestions only.
* Do not remove important functionality or essential process steps when recommending simplifications.
* Use plain, non-technical language.
* Avoid excessive detail; explanations should be simple while remaining understandable.

---

## Out of Scope

* Implementing code changes.
* Directly removing modules or functionality.
* Producing highly technical explanations or code-level analysis.
* Making unnecessary changes to processes that are already appropriate for the corresponding user level.

---

## Context & Dependencies

* The audit covers multiple user levels and accounts within the existing system.
* The first user level to investigate is the CEO.
* Available exploration agents are located in `.opencode\agents`.
* Audit reports must be stored in `docs\report`.

## Supporting Tasks

* [Tag: Sequential] Begin with the CEO account.
* [Tag: Sequential] Complete the CEO investigation and report before progressing through the remaining user levels in chronological order.
* Repeat the same audit approach for each remaining user level.

### Module Evaluation

* Determine what each module does for the selected user level.
* Determine whether the module is relevant to the responsibilities of that user level.
* Determine whether the module is necessary.
* Evaluate whether the module's workflow or process is appropriate.
* Identify processes that are unnecessarily complex.
* Identify opportunities to simplify or minimize the process while retaining important functionality and required steps.
* Recommend removal or revision when a module has no meaningful relationship or correlation with the corresponding user level.

### Reporting

* Record findings for the CEO in `docs\report\REPORT-CEO.md`.
* Create equivalent reports for each remaining user level.
* Present findings in chronological investigation order.
* Keep recommendations concise, practical, and understandable without technical terminology.

## Detailed Breakdown

### CEO Audit

Start with the CEO account and review its modules individually. For each module, first explain its purpose for the CEO in simple language. Then determine whether the process is appropriate, whether the module is necessary for the CEO's responsibilities, and whether the workflow is more complicated than necessary.

If the module is necessary and relevant, explain briefly why it should remain and identify any reasonable opportunities to simplify its process. If the module is unnecessary, unrelated, or has no meaningful correlation with the CEO's responsibilities, classify it as a recommendation for removal or revision rather than making an actual change.

### Remaining User-Level Audits

After completing the CEO audit, apply the same evaluation method to each remaining user level. Evaluate modules specifically in relation to the responsibilities and needs of that user level rather than assuming that a module necessary for one account is necessary for another.

### Recommendation Approach

Recommendations should focus on keeping only meaningful and necessary processes for each user level. Where simplification is possible, describe how the process could be reduced or made easier while preserving its important functions. Where a module appears unnecessary or unrelated, recommend removal or revision and briefly explain the reason.

### Investigation and Report Style

Keep every investigation ordered according to the sequence in which the user levels and modules are reviewed. Reports should use plain language and focus on what the module does, whether it belongs to that user level, whether its process is appropriate, and what should remain, change, simplify, or be considered for removal. Avoid code, implementation details, and excessive technical depth.
