# Objective

## Document Every Module’s Purpose, Ownership, User-Level Hierarchy, and Available Actions

---

## Role

You are a system documentation and audit analyst. Approach this objective by systematically examining each user level, page, module, interface control, and available action, then documenting their purpose and ownership in clear, simple language.

---

## Description

Create comprehensive Markdown documentation that explains the purpose and available actions of every module in the system. Begin by identifying and documenting the complete user-level hierarchy, starting with the CEO and continuing through every available user level. For each user level, review its accessible pages and modules, explain what each module is intended for, identify who handles or uses it, and describe what each available action or button does. Keep the explanations simple and practical so a reader can quickly understand the function of each module and interface control.

---

## Primary Objective

Produce a structured Markdown reference that documents every user level, module, module purpose, responsible user or role, and available action or button throughout the system.

---

## Secondary Objectives

* Establish the complete user-level hierarchy before documenting individual modules.
* Document modules beginning with the CEO level and continue through every other user level.
* Explain the purpose of each module within the context of the user level that accesses it.
* Identify who handles, manages, or uses each documented module.
* Document every available action and button within each module and explain what it does.
* Include buttons and other relevant actions directly in the documentation tables.

---

## Success Criteria

* A complete user-level hierarchy is documented first, beginning with the CEO and extending through every available user level.
* Every relevant page and module available to each user level is documented.
* Each module includes its page or route, module name, purpose, and responsible user or role.
* Every available button or actionable interface control within each module is included.
* Each documented action clearly explains what the action or button does.
* Module and action information is presented in tables where appropriate, including buttons within those tables.
* The completed documentation is saved as a Markdown file under `docs\ANALYZER\AUDIT - GLOBAL CAR EXCHANGE`.

---

## Constraints

* Use simple, clear descriptions for module purposes and actions.
* Do not omit buttons from the module documentation tables.
* Begin the analysis with the CEO user level before proceeding through the remaining user levels according to the identified hierarchy.
* Use sub-agents or multiple agents only during implementation or execution work, not during planning.

---

## Context & Dependencies

* The documentation must be based on the actual pages, modules, user levels, and interface actions available in the system.
* User-level access determines which pages and modules must be analyzed under each role.
* Page routes should be associated with their corresponding modules. For example, a route such as `http://localhost:3000/ceo/finance` would be documented under the CEO level and associated with the Finance module.
* The final Markdown documentation belongs in the existing `docs\ANALYZER\AUDIT - GLOBAL CAR EXCHANGE` documentation location.

## Supporting Tasks

### User-Level Hierarchy

* Identify every user level available in the system.
* Arrange the user levels into their correct hierarchy.
* Place the CEO at the beginning of the hierarchy.
* Use the completed hierarchy as the order for the subsequent module analysis.

### Page and Module Inventory

* For each user level, identify all pages or routes accessible to that user.
* Identify the module represented by each page or route.
* Associate each module with the user level that accesses or manages it.

### Module Purpose and Ownership

* Explain the purpose of each module in simple, practical language.
* Describe what the specific user level is expected to manage, review, monitor, or perform within the module.
* Identify the user level or role responsible for handling the module.

### Action and Button Analysis

* Inspect every actionable control available within each module.
* Document each button or action by its visible name or identifiable function.
* Explain clearly what happens or what function is performed when each action is used.
* Include buttons and actions in the corresponding module tables rather than documenting only the module itself.

### Markdown Documentation

* Organize the findings by user hierarchy, user level, page, and module.
* Use tables to make module purposes, ownership, buttons, and actions easy to review.
* Save the completed Markdown documentation under `docs\ANALYZER\AUDIT - GLOBAL CAR EXCHANGE`.

## Multi-Agent Feasibility Assessment

**Assessment:** YES. The implementation is suitable for multi-agent or sub-agent distribution because different user levels, pages, and modules can be inspected and documented independently once the user hierarchy and documentation structure have been established. Multi-agent execution must be limited to the implementation phase; planning and overall documentation structure should remain centralized.

**Parallelization Opportunities:**

* Assign separate user levels or groups of user levels to different agents for module discovery and documentation.
* Assign independent modules to separate agents when those modules do not depend on one another.
* Parallelize page inspection and button/action identification across different routes.
* Parallelize verification of module purposes, responsible roles, and available actions across independent functional areas.
* Consolidate independently produced module documentation into the final Markdown document after implementation-level analysis is complete.

**Dependencies to Manage:**

* Establish the complete user-level hierarchy before distributing implementation work.
* Maintain a consistent documentation format across all agents.
* Prevent duplicate coverage when modules or pages are accessible to multiple user levels.
* Ensure module descriptions distinguish role-specific behavior when the same module behaves differently for different users.
* Merge all implementation findings into a single coherent Markdown document.
* Verify that every documented button and action corresponds to the correct page, module, and user level.

**Named Sub-Agent Assignments:**

* **Hierarchy & Coverage Agent** (User-Level Inventory Specialist): During implementation, verify the complete user hierarchy and maintain coverage tracking so every user level and accessible page is accounted for.
* **Module Analysis Agent** (Functional Documentation Specialist): Analyze assigned modules and document their purpose, responsible user or role, and role-specific functionality.
* **Action Analysis Agent** (UI Interaction Specialist): Inspect assigned pages and document buttons, controls, and other available actions together with their functions.
* **Documentation Integration Agent** (Technical Documentation Specialist): Consolidate implementation findings into the required tables and Markdown structure while maintaining consistency across user levels and modules.
* **Coverage Verification Agent** (Audit and QA Specialist): Review the completed implementation documentation for missing pages, modules, buttons, actions, user levels, or inconsistent descriptions.

## Detailed Breakdown

### User-Level Hierarchy

The documentation must begin with a hierarchy of all user levels in the system. Start with the CEO and proceed through every remaining user level according to the system’s actual hierarchy. This hierarchy establishes the order in which the rest of the documentation should be organized.

### Per-User-Level Documentation

Create a dedicated section for each user level. Within that section, document every page and module that the user can access. Each entry should clearly associate the user level with the relevant page or route and module.

### Per-Module Documentation

For every module, document at minimum the following information:

| Field      | Required Detail                                                                |
| ---------- | ------------------------------------------------------------------------------ |
| Page       | The page or route where the module is accessed                                 |
| Module     | The module name                                                                |
| Handled By | The user level or role responsible for using or managing the module            |
| Purpose    | A simple explanation of why the module exists and what the user does within it |

The purpose description should be written in the context of the relevant user level. For example, if a Finance module is being documented under the CEO level, explain specifically how the CEO uses, manages, reviews, or interacts with that Finance module.

### Per-Action and Button Documentation

Within each module, include a table covering its buttons and other actionable controls.

| Action / Button           | Purpose                                                                        |
| ------------------------- | ------------------------------------------------------------------------------ |
| `<Button or Action Name>` | Explain clearly what this control does and what function it performs when used |

Document controls individually rather than grouping unrelated actions into a general description. For example, if a module contains `Record Entry` and `Request Disbursement` buttons, each button should have its own entry explaining its specific purpose.

### Required Documentation Pattern

For each module, follow a structure equivalent to:

**Page:**
`http://localhost:3000/ceo/finance`

**Module:**
Finance

**Handled By:**
CEO

**Purpose:**
Explain clearly what the Finance module allows the CEO to manage, review, monitor, or perform.

**Actions:**

| Action / Button      | Purpose                                            |
| -------------------- | -------------------------------------------------- |
| Record Entry         | Explain what the Record Entry action does.         |
| Request Disbursement | Explain what the Request Disbursement action does. |

Apply this pattern consistently to every discovered module and user level while adapting the content to the actual system behavior.

### Final Documentation Location

Place the completed Markdown file within:

`docs\ANALYZER\AUDIT - GLOBAL CAR EXCHANGE`

The final document should function as a clear reference for understanding the complete user hierarchy, what each module is for, who handles it, and what every available action or button does.
