# Objective
## Enhance and Standardize CEO Operations Pages

---

## Role

You are a frontend UI/UX engineer responsible for refining, standardizing, and debugging the CEO operations interface. Approach this objective with an emphasis on reusable components, consistency with existing customer-facing patterns, responsive interaction behavior, and reliable user actions.

---

## Description

Improve the CEO operations pages by applying existing reusable UI components and aligning their layouts and interaction patterns with corresponding customer-facing pages where specified. Standardize table presentation, contextual actions, confirmation dialogs, segmented controls, drawers, and spacing across the affected CEO pages. Resolve identified UI defects, including pagination lag, broken or unresponsive actions, overlapping content, inconsistent button sizing, and roadmap timeline issues. Reuse components and patterns that already exist in the system rather than introducing unnecessary alternative implementations.

---

## Primary Objective

Enhance and standardize the CEO operations interface across the specified pages by reusing existing system components, matching established customer-facing UI patterns, and fixing identified interaction and layout issues.

---

## Secondary Objectives

- Standardize applicable CEO data tables using the existing reusable table component.
- Align selected CEO page layouts with their corresponding customer-facing interfaces.
- Replace tab-based navigation with segmented controls where specified.
- Ensure confirmation-sensitive actions use the existing alert dialog component.
- Fix identified pagination, action, drawer, spacing, timeline, and layout defects.
- Preserve and reuse existing system components instead of recreating equivalent functionality.

---

## Success Criteria

- `/ceo/vehicles` uses the existing reusable table design, including action buttons and context menus.
- Pending vehicle records provide **View Details**, **Approve**, and **Reject** context-menu actions.
- Vehicle pagination no longer causes noticeable page lag when changing pages.
- Pending Price Approvals and Vehicles are separated through segmented controls for **Pending** and **Vehicles**.
- Publish, Approve, and Reject actions use the existing alert dialog component.
- `/ceo/inspections` uses the same reusable table component and visual pattern.
- `/ceo/inquiries` is redesigned to follow the customer inquiry page's chat-style interface.
- `/ceo/transactions` follows the customer transaction and invoice UI pattern and uses segmented controls instead of tabs.
- Transaction actions such as Approve and Cancel are verified and function correctly.
- `/ceo/roadmap` no longer displays the unwanted `") : ("` text.
- The bottom roadmap timeline is corrected.
- Drawer buttons on the roadmap page use the system's default button sizing.
- `/ceo/suppliers` uses the reusable table component.
- The supplier modal is replaced with a right-side drawer without overlapping content.
- Supplier page spacing is improved to reduce visual clutter.
- Supplier confirmations and other confirmation-required actions use the existing alert dialog component.

---

## Constraints

- Reuse the existing table component already implemented in the system.
- Reuse the existing alert dialog component for applicable confirmation actions.
- Follow existing customer-facing UI implementations where specifically requested.
- Use the system's default button sizing for the roadmap drawer buttons.
- Do not retain tabs where segmented controls are explicitly requested.

## Detailed Breakdown

### Reusable Table Standardization

Use the existing reusable table component for the CEO vehicle, inspection, and supplier pages. Preserve its established table layout, action-button behavior, and context-menu interaction rather than implementing page-specific alternatives. Configure page-specific actions through the reusable pattern while maintaining a consistent appearance and interaction model across the affected routes.

### Vehicle Page Navigation and Actions

The vehicle page should no longer display Pending Price Approvals and Vehicles together in the same continuous view. Introduce a segmented control with **Pending** and **Vehicles** states so users can switch cleanly between the two datasets. Pending entries should expose **View Details**, **Approve**, and **Reject** through the established context-menu pattern, while Publish, Approve, and Reject confirmations should use the alert dialog component already available in the application.

### Vehicle Pagination Performance

Investigate the current pagination implementation on the vehicle page and eliminate the lag that occurs when a user changes pages. The corrected interaction should preserve the expected pagination behavior without causing unnecessary page-level delays or degraded responsiveness.

### Inquiry Chat Interface

Replace the existing CEO inquiry interface with the same overall chat-style UI pattern used by the customer inquiry page. The redesign should follow the existing customer implementation closely so inquiry conversations remain visually and behaviorally consistent across both interfaces.

### Transaction and Invoice Interface

Update the CEO transactions page so its overall presentation follows the customer-facing transaction and invoice UI. Replace the current tab navigation with segmented controls. Verify the behavior of actions such as Approve and Cancel, repairing them if they currently fail to trigger and confirming that they operate correctly if the underlying implementation is already present.

### Roadmap Corrections

Remove the unintended `") : ("` text from the roadmap interface. Correct the bottom roadmap timeline so it displays and behaves as intended. Restore the drawer buttons to the application's standard button size rather than retaining the current overly thin sizing.

### Supplier Drawer and Layout

Replace the supplier modal with a right-side drawer while preserving the required supplier functionality. Resolve any overlapping content introduced by the current layout and refine spacing so the interface appears less cluttered. Confirmation-sensitive supplier actions should use the application's existing alert dialog component.
