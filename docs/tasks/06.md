# Objective
## Implement Role-Based URL Path Structure and Fix Authentication Issues

---

## Role
You are a full-stack developer responsible for debugging and fixing authentication, authorization, and routing issues in a vehicle management system. Approach this objective with a systematic investigation mindset, prioritizing security and role-based access control (RBAC) correctness.

---

## Description
The current system has multiple interconnected issues that require resolution. First, the hourly stables validation error persists despite previous fixes, and the root cause remains unidentified—whether it originates in the database, the seeded account configuration, or the application code requires thorough investigation. Second, the sidebar menu displays identically across all user accounts regardless of their assigned roles, which contradicts the documented role-based capabilities where each user type (Account Manager, CEO, Mechanic, etc.) should have distinct permissions and visible menu items. Third, the URL structure is problematic—instead of displaying a generic "/dashboard" for all users, the system should structure URLs with the role as the root path segment, such as `/admin/actual-page`, `/ceo/actual-page`, and `/account-manager/actual-page`, making it immediately clear which role the authenticated user belongs to. Fourth, there is a critical security vulnerability where unauthenticated users can access protected routes by manually entering URLs in the browser. All issues need systematic diagnosis and resolution while maintaining alignment with the project's documentation and design system.

---

## Primary Objective
Implement a role-based URL structure where each user role has its own root path segment (e.g., `/admin/`, `/ceo/`, `/account-manager/`), resolve the hourly stables validation error, fix the sidebar menu to display role-appropriate items, and secure all routes against unauthorized access.

---

## Secondary Objectives
- Identify the root cause of the hourly stables violation error by examining database records, seeded account configurations, and relevant code logic
- Ensure each user role (Account Manager, CEO, Mechanic, etc.) displays only the sidebar menu items they are authorized to access based on the documentation
- Restructure URL routing to use the user's role as the primary path segment (e.g., `/role-name/actual-page`) instead of a generic `/dashboard` pattern
- Implement proper authentication guards to prevent unauthenticated users from accessing protected routes via direct URL entry
- Update all affected documentation, including trackers, statuses, and roadmaps, to reflect the latest project state after fixes are implemented

## Detailed Breakdown

### Hourly Stables Error Investigation
The hourly stables validation error continues to persist despite previous attempts to fix it. A systematic investigation is required to determine whether the issue originates in the database (e.g., incorrect constraints, seed data corruption, or validation triggers), in the application code (e.g., validation logic, business rules implementation, or data handling), or in the seeded account configuration (e.g., test account settings that don't match production requirements). The investigation should examine error logs, database queries, validation rules, and compare seeded account data against production-like configurations to isolate the root cause.

### Role-Based URL Structure Implementation
The URL routing must be restructured from the current generic pattern to a role-based hierarchy where the role serves as the first path segment. For example, an Account Manager accessing their vehicle list should see `/account-manager/vehicles`, a CEO accessing the dashboard should see `/ceo/dashboard`, and an Admin accessing settings should see `/admin/settings`. This structure provides immediate visual identification of the user's role from the URL, supports better debugging and analytics tracking of role-specific user flows, and creates a more intuitive navigation experience. The implementation should include dynamic route generation based on the authenticated user's role and proper redirection for users attempting to access paths that don't match their role.

### Role-Based Access Control and Menu Visibility
The current system incorrectly displays the same sidebar menu items for all users regardless of their role. According to the documentation, each role (Account Manager, CEO, Mechanic, Admin, etc.) has distinct responsibilities and capabilities. The implementation should check the authenticated user's role against a permission matrix defined in the documentation and dynamically render only the menu items they are authorized to access. This includes verifying that vehicle creation capability is only available to roles that should have this permission, and that the sidebar accurately reflects the role's designated functions.

### Security Fix for Unauthenticated Access
A critical security vulnerability exists where unauthenticated users can access protected routes by manually entering URLs. The authentication middleware or route guards must be strengthened to verify that a valid session exists before allowing access to any protected route. This is especially important with the new role-based URL structure, as attackers might attempt to access various `/[role]/` paths. Unauthorized attempts should be redirected to the login page or return a 401 Unauthorized status. This should cover all protected routes, including the newly structured role-based URLs, and should not rely solely on client-side checks but implement server-side or server-rendered authentication validation where possible.
